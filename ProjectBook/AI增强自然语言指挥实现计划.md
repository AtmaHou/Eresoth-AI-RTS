# Project 咒令：AI 增强与自然语言指挥实现计划

> 文档类型：AI 功能专项设计与实施跟踪
> 基线日期：2026-09-06
> 当前基线：Eresoth RTS Phase 1 Demo
> 状态：设计中，先完成单机文字指挥，再接语音、联网和锦囊模式

## 0. 目标与非目标

### 0.1 目标

让玩家用自然语言表达“意图、优先级和条件”，由系统完成：

```text
自然语言/语音
    -> 意图解析
    -> 结构化军令
    -> 本地合法性校验与冲突仲裁
    -> 军团级战术执行
    -> 单位级微操
    -> 战报与请示
```

核心体验不是让大模型替玩家点击每个单位，而是让玩家像指挥官一样下达高层命令，把传统 RTS 的框选、拉阵型、分配目标、撤退和多线切换交给本地执行体。

### 0.2 非目标

- 不让 LLM 每帧控制单位。
- 不让 LLM 直接修改资源、生命值、位置或胜负状态。
- 不把 Unity 客户端直接连接第三方模型并暴露 API Key。
- 不在第一阶段同时实现语音、联机、锦囊和完整第二层科技。
- 不用自然语言替代所有传统操作；保留手动接管和快捷操作作为可靠兜底。

## 1. 当前基线与关键判断

### 1.1 已有可复用能力

| 当前能力 | 可复用位置 | 对 AI 的价值 |
| --- | --- | --- |
| 单位移动 | `Unit.CommandMove()` | 成为战术执行层的基础动作 |
| 单位攻击 | `Unit.CommandAttack()` | 统一攻击单位和建筑 |
| 工人采集 | `Worker` / `WorkerAI` | 支持资源分配、经济命令 |
| 建筑生产 | `Building.TryTrain()` | 支持生产计划执行 |
| 建筑建造 | `Game.BuildAt()` / `Game.BuildStructure()` | 支持建设命令 |
| 科技研究 | `Building.TryResearch()` | 支持科技优先级命令 |
| 自动反击 | `Unit.lastAttacker` / `NotifyAttacked()` | 支持本地战术兜底 |
| 脚本 AI | `EnemyAI` | 复用资源、出兵和防守规则 |
| 编队 | `SelectionManager` | 可迁移为军团的早期原型 |
| 数据驱动配置 | `Common.cs` / `GameConfig` | 生成可用单位、建筑、科技词表 |

### 1.2 当前缺口

当前代码仍然以“单个 Unit + 鼠标指令”为中心，不能直接支撑自然语言指挥。必须补充：

1. `Force`/`Army` 军团实体和稳定 ID。
2. 单位归属军团、军团编成和军团状态。
3. 地图语义点：主基地、资源点、入口、前线、撤退点等。
4. 战场态势摘要 `StateDigest`，不能把完整单位列表直接发给模型。
5. 版本化的 `CommandSchema`，所有模型输出必须是结构化军令。
6. 本地 `CommandValidator`、`CommandArbiter` 和过期处理。
7. 战术执行层，把军团命令拆成单位分配、移动、集火和撤退。
8. 事件系统，让 AI 只在重要事件或玩家新命令时调用模型。
9. 指令回放、日志和评测集，能够定位“模型理解错”还是“执行层做错”。
10. API 超时、模型不可用时的本地脚本策略和手动接管。

### 1.3 总体决策

采用**混合架构**：

- Unity 本地：模拟、校验、军团、战术 AI、执行和降级。
- 独立 AI Gateway：模型路由、鉴权、Prompt、结构化输出、日志和限流。
- 云端小模型：默认自然语言解析，低成本、低延迟。
- 云端强模型：复杂战略、模糊命令和战局复盘按需调用。
- 本地小模型：离线模式、开发测试和云端故障降级。
- 规则策略：所有模型失败时保证游戏继续运行。

## 2. 目标架构

```text
┌──────────────────────────────────────────────────────────┐
│ Unity 表现层                                             │
│ 文字输入 / 语音输入 / 指令历史 / 战报 / 确认与撤销        │
├──────────────────────────────────────────────────────────┤
│ Unity 指挥适配层                                         │
│ CommandClient / CommandValidator / CommandArbiter         │
│ StateDigestBuilder / EventBus / OrderJournal               │
├──────────────────────────────────────────────────────────┤
│ Unity 战术层                                             │
│ ForceManager / ForceController / Utility AI / 行为树       │
│ 编队、寻路、集火、护送、撤退、资源分配、生产执行           │
├──────────────────────────────────────────────────────────┤
│ Unity 模拟层                                             │
│ Game / Unit / Worker / Building / ResourceNode             │
├──────────────────────────────────────────────────────────┤
│ AI Gateway（独立进程或服务）                              │
│ Provider Router / Schema / Prompt / 重试 / 限流 / 审计      │
├──────────────────────────────────────────────────────────┤
│ 模型层                                                   │
│ 云端快速模型 / 云端强模型 / 本地 7B~14B 模型 / 规则降级    │
└──────────────────────────────────────────────────────────┘
```

### 2.1 数据流

```text
玩家输入
  -> CommandClient 生成请求
  -> StateDigestBuilder 提供压缩战况
  -> AI Gateway 选择模型
  -> 模型只输出 CommandSchema JSON
  -> Unity Schema 校验
  -> 游戏语义校验
  -> 冲突仲裁、补充确认或拒绝
  -> ForceController 执行军团级命令
  -> Unit.CommandMove / CommandAttack 等基础接口
  -> EventBus 产生进度与异常
  -> 战报生成器反馈玩家
```

### 2.2 延迟预算

| 路径 | 目标 | 说明 |
| --- | ---: | --- |
| 普通单位更新 | 每帧 | 完全本地，不访问模型 |
| 战术执行重评估 | 0.2~2 秒 | 完全本地 |
| 玩家普通文字命令 | 1~3 秒 | 快速模型 + 结构化输出 |
| 复杂多军团命令 | 3~8 秒 | 可升级到强模型，但先显示“处理中” |
| 紧急回防 | 0~300 毫秒 | 先由本地规则执行，模型只补充长期安排 |
| 战报生成 | 1~5 秒 | 异步，不阻塞军令执行 |

原则：**任何一条 LLM 请求都不应成为单位行动的前置条件。**

## 3. 核心领域模型

### 3.1 军团 `Force`

建议新增以下概念：

```text
Force
  id: army_1
  owner: Player / Enemy
  name: 一军团
  unitIds: []
  role: main / defense / raider / worker / reserve
  anchor: 当前中心点
  currentOrder: Order
  stance: aggressive / defensive / cautious / hold
  rallyPoint: 目标集合结点
  healthRatio: 平均生命比例
  lastReportAt: 最近一次汇报时间
```

每个单位增加：

- `forceId`
- `orderId`
- `role`，例如前排、远程、骑兵、工人、英雄
- `commandLockUntil`
- `isManualOverride`

军团不是简单的编队列表，而是命令、状态、目标、编成和执行进度的拥有者。

### 3.2 地图语义实体

自然语言不应要求模型猜坐标。地图生成后应注册稳定 ID：

```text
own_main_base
own_east_mana
enemy_main_base
enemy_west_wood
center_passage
north_choke
retreat_point_own_base
```

每个语义点包含位置、阵营、类型、可见性、危险度和当前占领状态。模型只引用 ID，Unity 负责把 ID 转成坐标。

### 3.3 结构化命令

建议所有命令统一使用以下字段：

```json
{
  "schema_version": 1,
  "request_id": "req_001",
  "orders": [
    {
      "order_id": "ord_001",
      "force_id": "army_2",
      "action": "harass",
      "target_id": "enemy_east_mana",
      "unit_filter": ["cavalry"],
      "priority": "high",
      "stance": "cautious",
      "conditions": [
        { "when": "enemy_main_force_seen", "then": "retreat" }
      ],
      "expires_after_seconds": 45,
      "fallback": "retreat_to_own_main_base"
    }
  ],
  "economy_plan": [],
  "clarification_needed": false,
  "player_reply": "二军团将骚扰敌方东侧魔法矿，发现主力后撤退。"
}
```

允许的 `action` 必须来自白名单。第一阶段只实现：

```text
move, attack, attack_move, defend, retreat, gather,
harass, escort, scout, focus_fire, regroup, hold,
train, research, build, cancel_order, request_report
```

## 4. 至少 20 种自然语言操作设计

下面的命令都应有明确的游戏效果、目标范围、失败反馈和传统操作对比。示例不是固定句式，模型需要理解同义表达。

| # | 玩家可以说 | 结构化意图 | 相比传统操作的优势 | 前置能力 |
|---:|---|---|---|---|
| 1 | “一军团去东边魔法矿，遇到主力就撤。” | 带条件的移动/骚扰 | 一句话表达目的地和撤退条件 | 军团、语义点、条件执行 |
| 2 | “让骑士绕后，弓箭手正面压制。” | 按兵种分工的协同攻击 | 不需要手动拆分部队和双线操作 | 编成筛选、角色分配 |
| 3 | “所有远程优先集火敌方英雄。” | 多军团统一集火 | 避免逐个选中远程单位 | 目标优先级、集火系统 |
| 4 | “二军团守住北口，敌人少于三队不要追出路口。” | 防守区域与追击阈值 | 传统操作难持续维持区域纪律 | 区域守卫、威胁评估 |
| 5 | “基地被攻击时，最近的部队回防，其他部队继续压矿。” | 事件触发的分层响应 | 同时处理主战场和基地告急 | 事件总线、自动分兵 |
| 6 | “农民优先保证木头，矿只留两个工人，兵营不停产。” | 经济目标和生产目标 | 省去频繁切换工人和建筑面板 | 经济计划、生产队列 |
| 7 | “木头低于一百时暂停扩军，先补农民和人口。” | 资源阈值策略 | 可持续执行，而不是一次性点击 | 资源条件、人口建筑 |
| 8 | “把残血单位撤到后方，满血单位继续围攻。” | 按生命值动态分层 | 自动拉扯和伤员管理 | 伤亡分组、治疗/修整点 |
| 9 | “先侦察中路，看到敌方骑兵就报告，不要交战。” | 低风险侦察 | 同时约束路径和交战规则 | 侦察状态、报告事件 |
| 10 | “三队步兵保护弓箭手推进，保持弓箭手不被骑兵碰到。” | 护卫编队 | 把保护关系交给执行体维护 | 护卫约束、威胁检测 |
| 11 | “把东矿附近的敌方工人赶走，不要打主基地。” | 经济骚扰目标 | 传统操作需要识别目标并控制追击 | 目标类型、禁止目标 |
| 12 | “如果敌方步兵超过十个，暂停骑士，改出长弓手。” | 对手构成响应 | 自动观察、转产和调整队列 | 可见情报、生产规划 |
| 13 | “所有部队在主基地外集合，等英雄复活/训练完成再进攻。” | 集结与等待条件 | 避免部队分批送死 | 集结点、等待条件 |
| 14 | “箭塔守东矿，主力不要离开基地防线。” | 建造与防守协同 | 同时完成选址、建造和驻防 | 建造规划、驻防区域 |
| 15 | “把一军团伪装成撤退，等敌人过桥后反包围。” | 诱敌/伏击策略 | 传统操作需要复杂时机和多队配合 | 伏击点、触发条件、军团姿态 |
| 16 | “敌人追得太深就关门，前排堵住，远程从侧面输出。” | 动态夹击 | 自然语言表达战术意图比逐点操作更快 | 阵型、区域约束、集火 |
| 17 | “二军团只攻击正在采集的工人，发现敌方骑兵就撤。” | 带禁止条件的骚扰 | 明确目标偏好和风险边界 | 目标筛选、撤退策略 |
| 18 | “把所有空闲工人派去最近的木材点，矿点至少留两人。” | 资源自动分配 | 不需要逐个拖选工人 | 工人分配器、资源约束 |
| 19 | “研究攻击科技优先，除非基地血量低于百分之四十。” | 条件科技计划 | 把长期策略交给系统持续执行 | 研究队列、条件计划 |
| 20 | “报告敌方最可能的进攻路线和我方最薄弱的防线。” | 战场分析请求 | 从原始信息中提炼判断，传统 UI 很难完成 | 情报摘要、分析模型 |
| 21 | “按照三步两弓一骑补充部队，缺矿时暂停骑士。” | 比例生产计划 | 不需要反复检查资源和兵种数量 | 生产配额、资源门槛 |
| 22 | “把一军团拆成两支：一半守家，一半跟我去中矿。” | 动态拆分军团 | 一句话完成选择、分组和任务分配 | 军团拆分、编成锁定 |
| 23 | “撤销所有去北路的命令，改为保护采集线。” | 批量撤销与改派 | 快速修正错误决策 | 命令日志、优先级仲裁 |
| 24 | “接下来三十秒只防守，除非敌方主基地空虚。” | 时间窗策略 | 适合应对短期侦察或反打 | 时间条件、风险判断 |
| 25 | “告诉我为什么二军团没有执行上一条命令。” | 可解释性查询 | 直接获得资源不足、目标消失等原因 | 执行日志、错误码、战报 |

### 4.1 第一批必须实现的命令

MVP 不应一次实现全部 25 种。建议第一批只做 1、2、3、4、6、8、9、11、18、19、23、25，共 12 种，覆盖移动、攻击、防守、经济、科技、撤销和解释。

### 4.2 有趣但应后置的命令

第 15、16、17、24 涉及伏击、诱敌、条件窗口和多个约束，体验价值高，但要求战术执行层成熟后再做，否则模型能听懂，游戏却执行不出差异。

## 5. 为自然语言优势必须补齐的基础玩法

### P0：没有这些就不要接模型

#### 5.1 军团系统

- 创建、命名、拆分、合并军团。
- 稳定 `force_id`，不能使用临时数组索引。
- 单位加入/离开军团。
- 军团编成统计：步兵、远程、骑兵、英雄、工人、总人口。
- 军团位置、平均血量、当前命令和执行进度。
- 军团手动接管和 AI 接管切换。

#### 5.2 语义地图与目标解析

- 所有资源点、基地、建筑和关键地形生成稳定 ID。
- “东矿、北口、家门口、敌方主力”等自然语言别名映射到 ID。
- 支持相对方向和区域，而不是让模型输出任意坐标。
- 为目标维护可见、已知、过期三种情报状态。

#### 5.3 命令执行基础设施

- `ICommand`、`OrderStatus`、`OrderPriority`。
- 命令生命周期：创建、排队、执行、暂停、完成、失败、取消、过期。
- 每个命令必须有 `order_id`、创建时间、来源、优先级和失败原因。
- 支持军团级命令转为单位级命令。
- 保留玩家手动命令的更高优先级覆盖开关。

#### 5.4 本地战术执行体

至少实现：

- 集合与跟随。
- 编队和角色站位。
- 目标选择与集火。
- 追击距离上限。
- 残血撤退。
- 防守半径。
- 遭遇敌方主力时的条件切换。
- 单位死亡、目标消失和路径失败后的重规划。

#### 5.5 事件和报告系统

统一产生事件：

```text
EnemySpotted
BaseUnderAttack
ResourceDepleted
ForceEngaged
ForceRetreated
OrderCompleted
OrderFailed
BuildingDestroyed
TechCompleted
```

事件必须包含时间、位置、相关实体、严重级别和可见范围，用于触发本地策略和生成战报。

### P1：提升自然语言的优势

- 资源阈值和生产计划。
- 目标优先级与禁止目标。
- 区域防守和巡逻。
- 侦察与战争迷雾。
- 编队模板：前排、远程、骑兵、工人、英雄。
- 阵型与局部避让，当前简单推挤不足以支持复杂协同。
- 可见性模型，避免模型利用玩家看不到的信息。
- 录像、回放、命令撤销和执行解释。
- 手动操作与自然语言命令的冲突处理。

### P2：支撑长期玩法

- 指挥所/通灵塔和 AI 指挥科技。
- 并行军令槽位。
- 语音输入和流式 ASR。
- 联机服务端权威校验。
- 锦囊模式的服务端离线模拟。
- 兵种特色技能的统一 Ability 接口。
- 更明确的地形、视野、道路、路口和高地语义。

## 6. 模型与 API 选型

### 6.1 推荐策略

| 场景 | 推荐模型 | 目的 |
| --- | --- | --- |
| 默认文字命令 | 云端快速、小型中文指令模型 | 低成本、低延迟、结构化 JSON |
| 复杂多军团策略 | 云端强模型按需调用 | 处理长期规划和模糊意图 |
| 离线模式/开发 | 本地 7B~14B Instruct 模型 | 无网络、隐私、故障降级 |
| 所有模型失败 | 规则解析器 + `EnemyAI` 类策略 | 游戏不中断 |

模型供应商通过 Provider 接口接入，不把业务代码绑定到某一家 API。优先选择支持以下能力的 API：

- JSON Schema 或 Function Calling。
- 稳定的中文指令理解。
- 较低首 Token 延迟。
- 流式输出。
- 可配置超时和重试。
- 明确的输入输出 Token 计费。
- 能关闭或限制自由文本输出。

### 6.2 本地还是云端

第一阶段选择**云端 API 为主、本地和规则降级**，理由：

- 当前最需要验证的是命令设计和战术执行，不是训练模型。
- 云端模型中文理解和复杂条件表达更稳定。
- 快速模型足以完成大多数结构化命令解析。
- 本地模型先作为离线和故障方案，不阻塞核心开发。
- API Key、Prompt 和路由逻辑可以集中在 AI Gateway，便于后续更换供应商。

纯本地部署应在以下条件满足后再作为默认选项评估：本地模型在项目测试集上命令解析准确率达到 95%，P95 响应时间满足目标，并且目标用户硬件覆盖率可接受。

### 6.3 AI Gateway 接口

Unity 不直接持有模型密钥，只调用自己的网关：

```http
POST /v1/commands/parse
Content-Type: application/json
```

请求：

```json
{
  "game_id": "local-session-001",
  "turn": 8420,
  "player_text": "二军团去东矿，遇到主力就撤",
  "state_digest": {},
  "available_actions": ["move", "harass", "retreat"],
  "schema_version": 1
}
```

响应：

```json
{
  "request_id": "req_001",
  "model": "fast-provider-model",
  "orders": [],
  "player_reply": "二军团将骚扰东侧魔法矿，发现敌方主力后撤退。",
  "confidence": 0.94,
  "clarification_needed": false,
  "usage": { "input_tokens": 0, "output_tokens": 0 }
}
```

`confidence` 只能作为是否追问的参考，不能替代本地合法性校验。

## 7. 实施阶段与验收标准

### A0：命令领域模型（1 周）

工作：

- 建立 `Force`、`Order`、`MapSemanticPoint`、`GameEvent`。
- 给单位、建筑、资源点增加稳定 ID。
- 建立命令状态机和错误码。
- 用硬编码 JSON 驱动一个军团移动和攻击。

验收：

- 不接模型也能执行 5 种结构化命令。
- 目标死亡、路径失败、单位不足时有明确失败原因。
- 命令可记录和重放。

### A1：本地战术执行层（2~3 周）

工作：

- 迁移当前 `SelectionManager` 编队逻辑为 `ForceManager` 原型。
- 实现防守、攻击、撤退、骚扰、护送、侦察。
- 接入 `Unit.CommandMove`、`Unit.CommandAttack` 和 `WorkerAI`。
- 增加残血撤退、追击半径和自动重组。

验收：

- 12 条第一批自然语言命令对应的 JSON 都能被本地执行。
- 模型完全离线时，战术执行仍可正常运行。
- 100 个单位场景下战术层不造成明显帧率下降。

### A2：态势摘要与校验仲裁（1~2 周）

工作：

- 实现 `StateDigestBuilder`，默认控制在 1~2K Token 等价信息量。
- 实现 JSON Schema 校验和游戏语义校验。
- 实现命令冲突、过期、重复和手动覆盖处理。
- 建立可见情报和事件增量摘要。

验收：

- 非法目标、敌方不可见目标、资源不足命令全部被拦截。
- 旧命令不会覆盖更高优先级的新命令。
- 失败原因可以显示给玩家。

### A3：云端快速模型接入（1~2 周）

工作：

- 建立 AI Gateway 和 Provider 接口。
- 接入一个支持中文结构化输出的快速模型。
- 记录请求、响应、耗时、Token、模型版本和执行结果。
- 增加超时、重试、限流、缓存和规则降级。

验收：

- 测试集命令解析准确率 >= 90%，目标版本 >= 95%。
- 普通命令 P95 从输入到结构化响应 <= 3 秒。
- API 断开后 3 秒内切换到本地规则策略。

### A4：自然语言 MVP（2 周）

工作：

- 上线 12 条第一批命令。
- 增加指令历史、撤销、确认和“为什么没执行”反馈。
- 增加战报和请示事件。
- 保留传统鼠标操作和手动接管。

验收：

- 可以完整玩一局“自然语言指挥 vs 脚本 AI”。
- 玩家不需要频繁打开多个面板即可完成经济、进攻、防守和撤退。
- 玩家明确知道系统当前正在执行什么。

### A5：复杂策略与语音（3~5 周）

工作：

- 增加条件命令、动态拆分、诱敌、夹击、资源阈值计划。
- 接入流式 ASR，语音结果复用同一 `CommandSchema`。
- 增加复杂命令升级强模型的路由规则。

验收：

- 复杂命令的执行成功率达到预设测试目标。
- 语音误识别可通过确认气泡和回退命令修正。
- 延迟不会阻塞已下发的战术行动。

### A6：联机与锦囊（后置）

工作：

- 将命令校验和战术执行迁移到服务端权威路径。
- 服务端保存完整命令日志和可验证状态摘要。
- 锦囊只允许白名单概念和结构化策略条件。
- 对局回放使用命令日志而不是模型重新生成结果。

验收：

- 客户端不能通过自然语言绕过资源、视野、科技和人口规则。
- 同一输入、地图种子和规则版本可复现结果。
- 模型服务不可用不影响已开始的对局。

## 8. 测试与评测体系

### 8.1 命令理解测试集

每种命令至少准备：

- 10 条标准表达。
- 10 条口语表达。
- 5 条省略主语或目标的表达。
- 5 条带冲突条件的表达。
- 5 条应该追问而不是猜测的表达。

例如“去东矿骚扰，看到大部队就回来”应覆盖“二军团”“东侧水晶”“敌方主力”“撤退到哪里”等省略情况。

### 8.2 必测指标

| 指标 | 目标 |
| --- | ---: |
| JSON Schema 合法率 | >= 99% |
| 核心命令意图正确率 | >= 95% |
| 非法命令拦截率 | 100% |
| 普通命令 P95 响应时间 | <= 3 秒 |
| API 故障切换时间 | <= 3 秒 |
| 命令执行可解释率 | >= 95% |
| 误执行严重命令 | 0 次 |
| 自然语言指挥完整对局成功率 | >= 90% |

### 8.3 评测必须区分三类错误

1. **理解错误**：模型把玩家意图解析错。
2. **校验错误**：非法命令没有被拦截，或合法命令被错误拒绝。
3. **执行错误**：命令正确，但军团没有按规则完成。

否则只看“模型回答对不对”会掩盖真正的工程问题。

## 9. 成本与可靠性策略

- 普通命令使用快速模型，强模型只处理复杂规划和低置信度请求。
- 态势摘要使用增量事件，不发送完整单位列表。
- 战报生成异步执行，不阻塞军令。
- 相同状态和相同意图可以短时间缓存。
- 请求设置超时、最大输出长度和每局调用预算。
- API Key 只放在 AI Gateway，客户端不保存。
- 模型输出始终经过 Schema 和游戏规则双重校验。
- 云端失败时先执行本地安全策略，再决定是否重试模型。
- 对话 Prompt、模型响应和执行结果可脱敏记录，用于回放和改进。

## 12. 最终落点

自然语言的巨大优势来自**持续目标、条件策略、跨面板协同和多线管理**，不是把“右键移动”换成一句话。实现顺序应当是：

```text
统一命令模型
  -> 军团和语义地图
  -> 本地战术执行
  -> 状态摘要与校验仲裁
  -> 云端快速模型
  -> 复杂条件与战报
  -> 语音、联机、锦囊
```

只要坚持“LLM 负责理解意图，本地系统负责决定能不能做和具体怎么做”，就能同时获得自然语言的表现力、RTS 的可控性、低延迟和可回放性。
