# Eresoth RTS 纯代码单位视觉设计与建模 Prompt

> 用途：将本文件完整提供给负责 Unity C# 程序化建模、视觉表现和单位动画的模型，作为视觉升级任务书。
> 项目：Eresoth RTS
> 当前引擎：Unity 6
> 当前视觉实现：C# 运行时创建 Mesh 和 Primitive，无外部美术资源依赖
> 视觉入口：`Assets/Scripts/Models.cs` 的 `Models.BuildUnit()`
> 运行时入口：`Assets/Scripts/Unit.cs` 的 `Unit.Spawn()`
> 相关工具：`Gfx.cs`、`BodyRig`、`Common.cs` 的 `UnitDef.prefab`

## 二、当前项目事实，必须先理解

### 2.1 当前单位类型

当前 `GameConfig` 中有：

#### 人族

- 农夫 `Farmer`：工人。
- 步兵 `Footman`：近战步兵。
- 长弓手 `Archer`：远程单位。
- 骑士 `Knight`：骑兵。
- 骑士团长 `LordKnight`：人族英雄，近战骑兵、AOE、攻击光环。

#### 不死族

- 侍僧 `Acolyte`：工人。
- 骷髅兵 `Skeleton`：近战步兵。
- 亡灵射手 `DarkArcher`：远程单位。
- 死亡骑士 `DeathKnight`：骑兵。
- 死亡游侠 `DeathRanger`：当前不死英雄配置，但本次视觉设计必须将其重新解释为**巫妖英雄**，不再设计成普通的死亡游侠或普通弓箭手。

### 2.2 当前程序化建模能力

`Models.cs` 当前已经有：

- `Models.BuildUnit()` 总入口。
- `HumanoidBase()` 人形基础结构。
- `BuildInfantry()`、`BuildRanged()`、`BuildCavalry()`、`BuildWorker()`。
- 人族和不死族的基础配色。
- `Gfx.Prim()` 创建内置几何体。
- `Gfx.MeshGo()` 创建自定义 Mesh。
- `Gfx.Frustum()`、`Gfx.Crystal()`、`Gfx.Roof()`、`Gfx.Quad()` 等程序化 Mesh。
- `BodyRig` 中的 `root`、`torso`、`head`、`legL`、`legR`、`armL`、`armR`、`horseLegs`。
- 部分材质支持金属、粗糙度、自发光和颜色变化。

目前存在的主要问题：

- 部分单位仍然容易看成“基础几何体叠加”。
- 人族与不死族的轮廓、材质和构造差异还不够强。
- 同一兵种内部的英雄升级感不够明显。
- 英雄目前主要依赖通用王冠、披风和肩甲，缺少专属武器、姿态、法器和轮廓。
- 远景 RTS 摄像机下，单位的阵营和兵种识别需要更强的轮廓语言。
- 需要更好的细节分层：远景轮廓、中景装备、近景装饰。
- 需要把视觉节点和动画节点明确分开，避免动画改变逻辑碰撞体。

## 三、总体美术方向

### 3.1 统一风格

采用：

```text
Stylized Low-Poly Fantasy RTS
+ hand-crafted silhouette
+ readable exaggerated proportions
+ layered procedural geometry
+ controlled bevels and faceted normals
+ rich faction materials
+ hero-grade focal details
```

不是写实扫描模型，也不是无细节的几何体。目标是“风格化、清晰、可信、有设计”的商业游戏单位。

视觉重点：

1. 第一眼看轮廓就能判断阵营和兵种。
2. 第二眼能看出武器、护具、职业和战斗方式。
3. 近距离观察能发现纹章、材质层次、法术符文、骨骼结构和局部不对称。
4. 英雄必须有普通单位没有的高度、姿态、颜色、装饰和主视觉道具。
5. 所有细节必须服务于识别度，不能变成随机装饰噪声。

### 3.2 造型比例

建议使用夸张但稳定的比例：

- 普通单位高度基准：`1.0`。
- 工人：`0.85~0.95`，重心低，装备简单。
- 普通步兵：`1.0`，肩宽和盾牌形成稳定轮廓。
- 普通远程：`1.0`，弓、箭袋和斗篷形成纵向识别线。
- 普通骑兵：`1.25~1.4`，马体和骑手必须整体可读。
- 英雄：普通同类单位的 `1.25~1.45` 倍视觉体量，不能仅靠缩放实现。

英雄必须同时拥有：

- 独特头部轮廓。
- 独特肩部或背部轮廓。
- 独特主武器/法器。
- 独特颜色焦点。
- 独特发光或粒子暗示。
- 独特站姿或动画挂点。

### 3.3 细节分层

每个单位模型按三层制作：

#### L0：远景识别层

从 RTS 摄像机的常规距离仍然可见：

- 阵营主色。
- 兵种轮廓。
- 盾、弓、骑枪、法杖、王冠等大形体。
- 英雄专属发光色。

#### L1：中景职业层

镜头靠近或选中单位时可见：

- 护甲片、绑带、斗篷、箭袋、骨骼层次。
- 人族纹章、布料分色、金属边缘。
- 不死族骨骼连接、符文、灵魂容器和腐蚀痕迹。

#### L2：近景商品层

用于英雄展示、胜利画面和 UI 预览：

- 专属武器纹路。
- 小型悬浮法器。
- 局部镂空和不对称结构。
- 材质粗糙度对比。
- 受控的发光、粒子、旋转和悬浮动画。

## 四、人族与不死族的核心差异

### 4.1 人族：秩序、工艺、纪律、阳光与实体结构

人族不是简单的“蓝色加金色”。请使用以下视觉语法：

- 结构：对称、铆接、锻造、木材、布料、石材。
- 轮廓：盾墙、旗帜、披风、尖顶、徽章、直线和整齐肩甲。
- 材质：抛光金属、皮革、织物、木材、暖石。
- 颜色：米白、铁灰、深蓝、红陶、金色暖光。
- 装饰：太阳/王冠/盾徽/剑纹/骑士团徽记。
- 动势：站姿稳定、武器握持明确、动作有训练有纪律。
- 不要：过度尖刺、无意义悬浮、随机骷髅装饰、紫绿死灵光。

人族的商业化关键词：

```text
reliable, noble, engineered, heraldic, readable, crafted, disciplined
```

### 4.2 不死族：巫妖、骨骼、灵魂、腐朽、寒冷魔法与非自然结构

不死族本次统一采用**巫妖美学**，尤其是英雄。不要把不死族做成普通紫色骑士或换色人族。请使用：

- 结构：骨骼支架、裂开的护甲、悬浮骨片、诅咒晶体、魂火容器。
- 轮廓：尖长肩甲、向外张开的骨刺、破碎披风、悬浮头冠、法杖和灵魂环。
- 材质：旧骨、黑曜石、腐蚀铁、破旧紫黑布、半透明灵魂晶体。
- 颜色：骨白、深紫、黑灰、幽绿、灵魂紫、少量冷蓝。
- 装饰：巫妖符文、灵魂瓶、骨冠、漂浮法环、裂隙和冰霜死灵纹。
- 动势：微量悬浮、衣摆滞后、魂火跳动、骨骼不自然地保持姿态。
- 不要：把所有不死单位都只做成“白骨 + 红眼 + 紫披风”。每种兵种必须有不同的骨骼构造、装备和职业语言。

不死族的商业化关键词：

```text
necromantic, elegant macabre, fractured anatomy, soul energy,
ancient lich empire, ritual geometry, spectral glow, unnatural motion
```

### 4.3 阵营材料规则

人族和不死族即使使用同一个兵种类别，也必须至少在以下五个维度上不同：

1. 基础形体语言。
2. 武器形态。
3. 材质粗糙度和边缘处理。
4. 发光颜色和能量来源。
5. 动画姿态和移动节奏。

## 五、兵种建模设计要求

### 5.1 工人

#### 人族农夫

- 草帽、皮围裙、卷起袖口、工具袋。
- 一侧挂斧头或锄头，另一侧背木材小捆。
- 颜色朴素但有暖色层次。
- 走路略微前倾，体现劳动者。
- 采集时工具动作和身体节奏要明显。

#### 不死侍僧

- 必须保持巫妖文明的低阶祭司感，而不是普通披袍人。
- 破损长袍、骨白手指、悬浮小魂灯、腰间灵魂瓶。
- 头部可以半遮面，只露冷色灵魂光。
- 下半身可以有轻微离地悬浮或烟雾底座，但不能影响碰撞和寻路。
- 采集动作应表现为“引导/收割灵魂能量”，而不是拿镐头挖矿。

### 5.2 步兵

#### 人族步兵

- 盾牌必须是最大识别元素之一。
- 盾面有清晰的人族纹章，并使用双色或三色分区。
- 头盔应有护鼻、护颈或短羽饰，避免无特征方块头。
- 胸甲、护肩、护臂和腿甲形成明确层级。
- 剑身、剑柄、护手要能在中景看出。
- 轮廓偏稳定、宽肩、重心扎实。

#### 不死骷髅兵

- 不要仅用人族骨白换色版本。
- 骨架应明显裸露：肋骨、脊柱、肩胛、膝骨至少有两处可见。
- 盾牌可以是骨盾或墓碑碎片盾，边缘参差不齐。
- 武器应有锈蚀、断裂、重新绑扎的痕迹。
- 一只肩膀或一条腿可以略有不对称，表现拼接和腐朽。
- 眼部发光不能取代面部结构。

### 5.3 远程单位

#### 人族长弓手

- 长弓是纵向轮廓核心，弓弦要清晰。
- 箭袋、护腕、手套、披肩和轻甲形成职业层次。
- 使用绿色、深木和皮革，但避免和环境完全融为一体。
- 站姿略侧身，拉弓时肩部和手臂挂点要自然。
- 箭头、羽饰或小旗可以作为远景识别点。

#### 不死亡灵射手

- 统一巫妖体系：骨弓应像由肋骨、指骨或晶体拼成。
- 斗篷不是普通布片，要有破碎边、内侧灵魂纹和轻微悬浮。
- 箭矢可以是紫色灵魂箭或骨箭，但要保持可读性。
- 眼窝、胸腔或箭头处形成冷色发光点。
- 拉弓姿态应带有不自然的关节角度和悬浮感，但不能滑稽。

### 5.4 骑兵

#### 人族骑士

- 马体、马头、缰绳、马鞍、骑手、骑枪必须形成整体。
- 使用人族纹章马衣或胸甲，骑手与坐骑颜色要有层次对比。
- 骑枪必须明显长于普通剑，形成突击兵种识别。
- 马腿挂点和骑手身体挂点分开，支持冲锋和攻击动画。
- 轮廓向前，表现速度和冲锋。

#### 不死死亡骑士

- 仍然属于巫妖文明，不是简单黑色人族骑士。
- 坐骑可以是骨马、腐化战马或黑曜骨甲马，但必须保留马的头、颈、胸和腿的可读结构。
- 皮肤/骨骼、黑甲、破碎旗帜、紫色魂火和符文剑形成对比。
- 马眼、胸腔、蹄部可有幽绿或灵魂紫光。
- 骑手头盔采用骨冠/尖角/悬浮碎片，不使用普通人族羽饰。
- 攻击姿势应比人族骑士更不稳定、更像被死灵能量驱动。

## 六、英雄单位：必须重点重做

英雄不能只是普通单位加大、加王冠、加披风。英雄必须有独立的角色设计、专属几何结构、专属颜色焦点、专属武器和专属动画节点。

### 6.1 人族英雄：骑士团长 LordKnight

角色关键词：

```text
圣辉骑士团长、战场旗帜、重型骑士、纪律核心、太阳金属、冲锋领袖
```

视觉要求：

- 体量明显大于普通骑士，但不能只是整体放大。
- 头盔必须有独特冠饰、面甲或高耸羽冠。
- 胸甲有大型人族徽记，建议使用太阳、王冠或骑士团纹章。
- 肩甲、护臂、护腿比普通骑士更完整，但保持可读轮廓。
- 背部有短披风或分层战旗，颜色以红、深蓝、金为主。
- 主武器为专属重型骑枪或圣辉长剑，必须比普通骑士武器更醒目。
- 攻击光环用金色环形符文、细小旗帜纹路或暖色粒子表达。
- AOE 近战攻击可在武器挥击时产生短促的金色弧光，但不要大面积遮挡模型。
- 站姿挺拔、脚下稳定，体现“军团核心”。
- 动画挂点至少增加：`weaponMain`、`banner`、`auraOrigin`、`cape`。

建议细节：

- 胸甲中央做三层结构：底板、纹章、发光细线。
- 头盔顶部做可辨识的冠状结构，而不是四个小方柱。
- 披风底部使用 3~5 个不规则分片，行走时轻微摆动。
- 骑枪尖端做金属锥体，枪杆连接处有金色绑带。
- 鞍具和马甲上增加人族纹章，但不要把纹章做成过细无法看见的纹理。

### 6.2 不死英雄：巫妖 DeathRanger 视觉重定义

**必须将当前 `DeathRanger` 重新解释为巫妖英雄。不要再按“死亡游侠”制作。**

角色关键词：

```text
古代巫妖王、灵魂收藏者、冰冷法术、悬浮骨冠、破碎法袍、灵魂法杖、死灵核心
```

建议名称显示可以改为：

```text
“霜骨巫妖” / “低语巫妖” / “灵魂大法师”
```

除非需要兼容存档，否则不要修改内部 ID `deathranger`；优先修改显示名和视觉实现。

视觉结构必须包含：

1. **巫妖头部**
   - 细长、非人类比例的头骨。
   - 眼窝使用幽绿或灵魂紫双层发光。
   - 下颌、额骨和颧骨有明确结构，不要用一个白色方块代替。
   - 头部周围有悬浮骨冠或碎裂王冠，碎片不完全对称。

2. **身体和法袍**
   - 身体可以悬浮在破碎法袍和灵魂烟雾中。
   - 法袍下摆做 5~7 个分片或尖角，形成倒三角轮廓。
   - 袍面使用深紫黑、旧布紫和冷灰层级。
   - 内层露出肋骨、胸腔或死灵核心。

3. **灵魂核心**
   - 胸口或腹部放置一枚可见的灵魂晶体/命匣核心。
   - 核心使用半透明或自发光材质。
   - 核心应有缓慢旋转、脉动或内层颜色变化。
   - 不能让核心穿过身体或被肩甲完全遮挡。

4. **主法器**
   - 使用巫妖法杖、灵魂镰、骨制权杖或浮空法典之一作为主武器。
   - 法杖应有顶部晶体、骨环、符文和悬浮小碎片。
   - 法器必须有专属挂点 `staff` 或 `relic`，供攻击动画和弹道起点使用。
   - 远程攻击时，弹道从法器/手部/胸口核心中的明确位置发出。

5. **肩部和背部**
   - 使用尖长骨肩甲、悬浮骨片或背部灵魂环。
   - 背部可以有 3~5 个悬浮符文碎片，形成英雄远景识别轮廓。
   - 不要把背部做成普通矩形披风。

6. **攻击光环**
   - 当前英雄有 `auraRadius` 和攻击加成，视觉上必须让玩家理解这是光环。
   - 在脚下或胸口下方生成低矮的紫绿双层符文环。
   - 使用低亮度持续发光，避免遮挡战斗和血条。
   - 英雄移动时光环跟随，攻击时短暂脉冲。

7. **远程 AOE**
   - 当前英雄有远程攻击和 `aoeRadius`。
   - 弹道可以是灵魂箭、骨矛、冰霜灵火或碎裂法术球。
   - 命中时建议用小范围环形符文、骨片或魂火爆裂表达溅射。
   - 视觉效果应由独立方法生成，不能把战斗数值逻辑写入模型类。

巫妖整体必须表现为“古老、强大、危险、优雅而非滑稽”。避免廉价的骷髅王、普通法师、紫色换皮弓箭手和过多发光导致的视觉过曝。

## 七、程序化建模技术要求

### 7.1 优先从 Primitive 组合升级为自定义 Mesh

对于重复且需要轮廓控制的部件，优先增加可复用 Mesh 工具：

- 棱柱、截锥、尖刺、骨片。
- 带厚度的盾牌和披风片。
- 弧形弓、弯曲法杖、骨弓。
- 具有中心线和半径的环形符文。
- 挤出式徽章和胸甲。
- 低多边形马头、蹄、骨骼关节。
- 断裂晶体和不规则多面体。

所有 Mesh 必须：

- 正确设置顶点、三角形、法线。
- 必要时生成 UV 或合理使用材质颜色。
- 避免反向面和明显穿模。
- 使用稳定的局部坐标，便于挂点动画。
- 不给纯装饰 Mesh 添加 Collider。

### 7.2 建立可复用的构件库

建议在 `Models.cs` 中增加或整理以下工具：

```text
CreateTaperedLimb()
CreateFacetedSkull()
CreateBoneRibCage()
CreateShieldWithEmblem()
CreateLayeredCape()
CreateCurvedBow()
CreateLance()
CreateRuneRing()
CreateSoulCrystal()
CreateFloatingShard()
CreateHornedHelmet()
CreateLichCrown()
CreateLichStaff()
CreateHorseBody()
CreateArmorPlate()
CreateBanner()
```

不要为每个单位重复复制几十行 Primitive 创建代码。构件库必须支持尺寸、颜色、材质、旋转、镜像和随机种子参数。

### 7.3 材质和颜色

扩展 `Gfx` 时建议保留统一材质缓存，但允许控制：

```text
baseColor
metallic
smoothness
emissionColor
emissionStrength
alpha/cutout（仅在确有必要时）
```

推荐材质分层：

#### 人族

- 皮肤：暖色、低金属、中粗糙。
- 布料：深蓝/红色、中高粗糙。
- 金属：铁灰、高金属、中低粗糙。
- 金饰：暖金、高金属、中低粗糙。
- 法术：金白或暖黄，自发光但克制。

#### 不死族

- 骨骼：骨白、中高粗糙，不要纯白。
- 腐蚀铁：黑灰、金属、高粗糙。
- 黑曜石：低亮深色、较高金属。
- 旧法袍：深紫黑、高粗糙。
- 灵魂能量：幽绿/灵魂紫，自发光。
- 晶体：冷色、透明感或高光感，但要考虑内置/URP 兼容性。

### 7.4 自发光约束

- 自发光只用于眼睛、符文、灵魂核心、法器和英雄光环。
- 普通单位发光点少于英雄。
- 发光不能覆盖轮廓，也不能导致敌我颜色难以区分。
- 如果透明材质在当前管线不稳定，优先用实体晶体 + 自发光替代真正透明。

### 7.5 动画挂点

扩展 `BodyRig` 时，建议增加：

```csharp
public Transform weaponMain;
public Transform weaponOff;
public Transform staff;
public Transform relic;
public Transform banner;
public Transform cape;
public Transform auraOrigin;
public Transform projectileOrigin;
public Transform soulCore;
public Transform[] floatingParts;
```

这些挂点只用于视觉和动画：

- 移动时摆臂、摆腿、马腿和披风。
- 攻击时武器、法器、枪尖前冲。
- 远程弹道从 `projectileOrigin` 发出。
- 英雄光环从 `auraOrigin` 控制。
- 巫妖魂核和悬浮碎片独立旋转/脉动。

不要让视觉子节点承担单位碰撞、路径或战斗判定。

## 八、具体改造命令

下面的命令可以直接作为后续模型的执行清单。执行时必须先读取现有代码，再逐项修改和验证。

### 命令 A：建立单位视觉架构

> 阅读 `Models.cs`、`Gfx.cs`、`Unit.cs` 和 `Common.cs`。保留现有公共入口，整理 `Models.BuildUnit()` 为“阵营 + 兵种 + 英雄专属分派”的清晰结构。把通用构件提取成可复用方法，增加 `BodyRig` 的武器、法器、披风、旗帜、光环、魂核和弹道挂点。不要修改单位战斗规则。

### 命令 B：升级人族三类普通单位

> 重做人族农夫、步兵、长弓手和骑士的程序化模型。每个单位至少增加 3 个职业识别细节和 1 个远景轮廓特征。使用人族的锻造、徽章、木材、布料和暖金材料语言，避免简单换色。确保模型从 RTS 摄像机距离仍能区分工人、步兵、远程和骑兵。

### 命令 C：升级不死族为统一巫妖文明

> 重做不死侍僧、骷髅兵、亡灵射手和死亡骑士，使其属于同一个巫妖文明但职业差异明显。统一使用骨骼、灵魂、腐蚀铁、破碎法袍、符文和幽光语言；禁止只把人族模型改成紫色或加红眼。每个不死单位至少增加一种独特骨骼结构和一种专属死灵装备。

### 命令 D：重做不死英雄为巫妖

> 将 `GameConfig.DeathRanger` 的显示定位改为巫妖英雄，但保留内部 ID `deathranger` 以避免破坏引用。重做 `Models.AddHeroDecor()` 和不死英雄分支：制作细长头骨、悬浮骨冠、破碎法袍、可见灵魂核心、专属巫妖法杖、悬浮骨片、紫绿双层光环和远程法术弹道挂点。不要制作成普通亡灵射手、死亡骑士或仅仅放大的骷髅。

### 命令 E：重做人族英雄

> 将 `LordKnight` 设计为人族军团视觉中心。增加专属重型头盔、骑士团胸甲纹章、分层肩甲、战旗或短披风、圣辉骑枪/长剑、专属马甲和金色攻击光环。英雄必须通过体量、颜色、轮廓、武器和姿态同时区别于普通骑士。

### 命令 F：加入低成本英雄表现

> 增加不依赖外部资源的轻量视觉表现：英雄魂核脉动、符文环旋转、法杖晶体闪烁、披风摆动、悬浮碎片慢速环绕、攻击时短促脉冲。表现必须可复用、可关闭、无逻辑副作用，并控制 GameObject 数量和材质实例数量。

### 命令 G：优化远景识别和性能

> 从默认 RTS 摄像机距离检查所有单位轮廓。优先保证大形体、颜色分块和武器方向，删除远景不可见的小装饰。为普通单位和英雄设定细节预算；通过共享 Mesh、共享 Material、减少重复对象和必要的 LOD/简化策略控制性能。不要为了近景细节破坏百单位同屏。

### 命令 H：建立视觉验收场景

> 在编辑器中增加一个只用于视觉评审的单位展示场景或工具：人族/不死族所有普通单位、两个英雄、正面/侧面/背面、近景/远景、站立/移动/攻击状态。展示阵营配色、材质、自发光、阴影、轮廓和血条遮挡问题。不要把展示逻辑混入战斗代码。

### 命令 I：修复穿模、漂浮和动画问题

> 逐个检查头盔、武器、盾牌、弓、法杖、披风、马腿、魂核和光环。修复明显穿模、悬浮、反向法线、错误父子坐标和动画时抖动。视觉节点与 `Unit` 根节点分离，碰撞体只保留在逻辑根节点。

### 命令 J：输出改造报告

> 完成后输出：修改文件、增加的类/方法/字段、每个单位的视觉差异、英雄专属设计、性能估算、已知限制、Unity 管线兼容性、如何运行展示场景、如何回滚。不要只说“完成”，必须列出可审查的技术结果。

## 九、AI 执行协议：让模型更有效、更少出错

你必须按以下顺序执行，不允许一次性重写整个 `Models.cs`：

### 9.1 先建立基线

1. 读取 `Models.cs`、`Gfx.cs`、`Unit.cs`、`Common.cs` 的当前版本。
2. 找到 `Models.BuildUnit()`、`BodyRig`、`Unit.Spawn()` 和所有 `Gfx` 公共方法。
3. 记录当前可编译状态、已有材质接口、已有 Mesh 工具和现有英雄表现。
4. 先只输出“现状问题清单 + 拟修改方法 + 风险”，不要立即大范围改代码。

### 9.2 分阶段执行

每次只完成一个垂直切片：

```text
基础构件工具
   -> 一个普通人族单位
   -> 一个普通不死单位
   -> 人族英雄
   -> 巫妖英雄
   -> 其余单位批量迁移
   -> 展示场景和质量检查
```

每个切片必须：

- 使用共享构件方法，不复制大段代码。
- 保留旧入口或提供兼容包装方法。
- 修改后立即进行 Unity 编译检查。
- 检查 Console 是否有异常、MissingReference、Shader 或 Mesh 警告。
- 在近景和 RTS 远景各检查一次。
- 只在当前切片通过后再开始下一个切片。

### 9.3 模型的输出格式

每次修改前先输出：

```text
本次切片：
目标单位：
要解决的视觉问题：
准备复用/新增的构件：
会修改的文件：
不会修改的玩法接口：
质量检查方式：
```

每次修改后必须输出：

```text
已修改文件：
新增方法/字段：
已实现的轮廓差异：
已实现的阵营差异：
已实现的英雄差异：
编译结果：
质量检查结果：
未解决问题：
下一步：
```

### 9.4 AI 使用便利性约束

- 优先使用命名明确的构件方法，不要求后续模型阅读几百行重复 Primitive 代码。
- 每个单位的视觉入口必须保持在 `BuildUnit()` 的清晰分派中。
- 每个重要视觉部件必须有语义命名，例如 `lichSoulCore`、`humanBanner`，禁止全部叫 `part1`、`cube2`。
- 将材质、Mesh、挂点和动画表现分开，后续模型才能安全修改其中一层。
- 对同一个英雄的视觉修改必须集中在英雄专属方法，不要散落到普通兵种方法。
- 新增颜色、材质和 Mesh 时说明复用策略，避免每次运行产生无穷实例。
- 不确定时优先询问或输出候选方案，不要自行删除已有视觉结构。

## 十、自动化建模质量检查模块

不要只依赖模型自我判断“看起来不错”。请新增一个只在编辑器或开发构建中运行的质量检查模块，建议文件：

```text
Assets/Editor/VisualModelQualityCheck.cs
Assets/Editor/VisualModelPreviewWindow.cs（可选）
```

它不参与正式运行时战斗逻辑，不应给单位添加碰撞或改变游戏状态。

### 10.1 检查入口

提供菜单或编辑器按钮：

```text
工具 / Eresoth RTS / Visual Model Quality Check
```

至少提供三个模式：

1. **静态结构检查**：不运行游戏，检查 Transform、Renderer、Mesh、材质和挂点。
2. **运行时生成检查**：生成所有单位和英雄临时预览，检查视觉节点和组件。
3. **展示截图检查**：从正面、侧面、背面、近景、远景生成预览，供人工复核。

### 10.2 检查等级

```text
ERROR   必须修复，例如空 Mesh、异常尺寸、缺少英雄挂点
WARNING 建议修复，例如材质实例过多、细节超预算
INFO    记录，例如普通单位构件数量和共享材质数量
```

### 10.3 几何和 Transform 检查

对每个生成的单位执行：

- 根节点存在且只有一个逻辑根节点。
- 视觉节点位于 `visual` 层级，不把视觉子部件挂到逻辑根节点之外。
- 所有 Transform 的 position、rotation、scale 都是有限数值，不能出现 NaN 或 Infinity。
- scale 不能为零，不能出现负缩放导致法线和镜像错误。
- Renderer 的 bounds 不为空，模型高度和宽度在单位预期范围内。
- 所有 Mesh 至少有有效顶点和三角形。
- 三角形索引不能越界。
- Mesh bounds、normals 和顶点数量一致。
- 检测明显的零面积三角形、反向面和异常超大面。
- 检查模型是否整体漂浮、陷入地面或低于预期基准线。
- 检查英雄是否确实比同类普通单位更有视觉体量，而不是只改变数值。

建议尺寸基线：

```text
普通单位高度：0.6 ~ 3.5 * def.size
英雄单位高度：0.9 ~ 5.0 * def.size
模型中心到根节点水平偏移：<= 0.8 * def.size
脚底/悬浮底座高度：0 ~ 0.25 * def.size
```

尺寸范围应配置化，不要把检查阈值散落在检查代码中。

### 10.4 碰撞和逻辑隔离检查

- 视觉装饰节点不能有 `Collider`、`Rigidbody`、`NavMeshAgent` 或战斗脚本。
- 逻辑根节点最多保留 `Unit` 要求的碰撞体。
- `ring`、光环、披风、魂火、悬浮碎片不能改变逻辑根节点 bounds。
- `BodyRig` 挂点必须是视觉节点的子节点。
- 删除或替换视觉模型后，`Unit`、`Worker` 和 `ITargetable` 仍然存在。
- `projectileOrigin`、`auraOrigin`、`soulCore` 等挂点缺失时必须报告 ERROR，而不是静默跳过。

### 10.5 阵营和兵种识别检查

为每个单位记录视觉标签：

```text
team: human / undead
kind: worker / infantry / ranged / cavalry
hero: true / false
```

检查规则：

- 人族和不死族不能只靠颜色区分，至少要有结构或装备差异。
- 同阵营的步兵、远程、骑兵必须有不同主轮廓。
- 英雄必须有至少两个普通单位没有的识别部件。
- 巫妖必须存在头骨、魂核、法器、骨冠/悬浮碎片中的至少三类。
- 人族英雄必须存在专属纹章、英雄武器、旗帜/披风、英雄头部中的至少三类。
- 远景状态下，兵种主轮廓不能被光环或特效覆盖。

检查模块可以输出一个识别矩阵：

```text
                        人族      不死族    是否英雄    轮廓部件数    主材质数
Worker          PASS      PASS      NO          ...           ...
Infantry        PASS      PASS      NO          ...           ...
Ranged          PASS      PASS      NO          ...           ...
Cavalry         PASS      PASS      NO          ...           ...
Hero            PASS      PASS      YES         ...           ...
```

### 10.6 材质、Shader 和发光检查

- Renderer 必须有材质，材质必须有有效 Shader。
- 当前渲染管线下 Shader 不存在时报告 ERROR。
- 不允许每个单位都创建新的等价材质实例。
- 统计每个单位的 Renderer、Material、Shader 数量。
- 自发光只允许出现在眼睛、符文、魂核、法器、光环和英雄特效部件。
- 发光强度不能使模型主体轮廓丢失。
- 不死族幽绿和灵魂紫不能同时覆盖全身。
- 人族金色高光不能把普通骑士和英雄混成同一亮度。
- 如果使用透明材质，检查排序、双面、深度写入和 URP/内置管线兼容性；不稳定时退回实体晶体 + 自发光。

### 10.7 动画挂点检查

普通单位按类型检查：

```text
Worker:      torso, head, tool 或 resourceTool
Infantry:    torso, head, armL, armR, weaponMain, weaponOff
Ranged:      torso, head, armL, armR, weaponMain, projectileOrigin
Cavalry:     torso, head, armR, horseLegs, weaponMain
```

英雄额外检查：

```text
weaponMain, projectileOrigin, auraOrigin,
cape 或 banner, soulCore/heroCore
```

执行一个最小动画探测：

- 摆动每个腿/马腿挂点。
- 摆动双臂和武器挂点。
- 旋转披风、旗帜和悬浮碎片。
- 让弹道从 `projectileOrigin` 发射到目标。
- 让光环围绕 `auraOrigin` 旋转。

任何挂点旋转导致逻辑根节点、碰撞体或寻路位置变化，都报告 ERROR。

### 10.8 性能预算检查

默认开发预算，允许根据实际 Profiling 调整：

| 对象 | Renderer | 材质槽 | 自发光/特效节点 | 目标 |
| --- | ---: | ---: | ---: | --- |
| 普通单位 | <= 12 | <= 4 | <= 3 | 可批量生成 |
| 普通骑兵 | <= 18 | <= 5 | <= 3 | 马和骑手合并考虑 |
| 英雄 | <= 28 | <= 7 | <= 10 | 近景重点对象 |
| 100 单位总计 | <= 1400 | 尽可能共享 | 可控 | 不因视觉明显掉帧 |

检查并报告：

- GameObject 数量。
- Renderer 数量。
- Mesh 数量和三角形数量。
- 材质实例数量。
- 自发光和粒子对象数量。
- 是否在 `Update()` 中重复创建 Mesh、材质或 GameObject。

### 10.9 输出格式

质量检查必须输出机器可读和人类可读结果：

```text
[ERROR] DeathRanger 缺少 projectileOrigin
[ERROR] Skeleton 的装饰节点 BoneRib_03 含 Collider
[WARNING] LordKnight 使用了 31 个 Renderer，超过英雄预算 28
[WARNING] Human Footman 与 Human LordKnight 的主色差异不足
[INFO] 所有普通单位共享 6 个材质实例

Summary:
ERROR=2 WARNING=2 INFO=1 PASS=false
```

只有 `ERROR=0` 才能进入下一阶段；`WARNING` 必须在报告中解释是否接受。

### 10.10 质量检查命令

> 新增 `VisualModelQualityCheck.cs`，提供编辑器菜单，自动生成人族/不死族全部单位和两个英雄的临时对象，执行几何、组件隔离、材质、挂点、识别度和性能预算检查。检查完成后输出 Console 摘要，并把完整报告写到 `ProjectBook/VisualModelQualityReport.md` 或 `Library` 下的开发报告目录。检查器失败不能修改正式场景或游戏状态。

## 十一、商用级质量门槛

### 9.1 视觉验收

每个普通单位必须满足：

- 3 秒内能看出阵营。
- 3 秒内能看出兵种类别。
- 不靠名称标签也能区分人族和不死族。
- 正面、侧面、背面没有明显空洞或穿模。
- 武器方向和攻击方式一致。
- 颜色在不同光照下仍可读。

每个英雄必须满足：

- 从同类普通单位中一眼跳出。
- 有专属轮廓、武器、头部、背部和颜色焦点。
- 有至少一个非对称但合理的设计元素。
- 有专属光环或灵魂能量表现。
- 近景有可讲述的角色细节。
- 远景不会因特效过多而失去轮廓。

### 9.2 技术验收

- 不破坏现有编译和运行时逻辑。
- 不给装饰几何体添加 Collider。
- 不为同一种颜色和材质无限创建实例。
- 不让视觉节点影响 `Unit` 根节点的位置和碰撞。
- 不出现 NaN、反向三角面或明显 Z-fighting。
- 100 个单位同屏时保持可接受帧率。
- 人族和不死族材质在当前内置管线/URP 下都能正确显示。
- 英雄视觉特效可独立开关。

### 9.3 禁止事项

- 禁止从网上复制受版权保护的具体角色模型、纹理、代码或品牌视觉。
- 禁止直接仿制 Warcraft、Warhammer、魔兽世界、英雄联盟等商业角色的独特外观。
- 可以参考公开技术方法、几何构造和抽象美术原则，但最终设计必须原创。
- 不要引入大体积外部资产来逃避纯代码建模要求。
- 不要把所有单位做成同样的头、身、手、武器模板后只改颜色。
- 不要使用大量随机细节掩盖设计不足。
- 不要用过度发光、粒子或透明材质替代清晰几何结构。

### 12.1 Unity 官方：运行时 Mesh 的最小正确实现

### 12.2 Catlike Coding：可直接迁移的几何构件教程

- [BufferGeometry](https://threejs.org/examples/webgl_buffergeometry.html)

## 十一、最终执行格式

完成任何一次模型升级后，必须按以下格式汇报：

```text
1. 本次修改的视觉目标
2. 修改的文件和方法
3. 人族与不死族分别增加了什么差异
4. 普通兵种分别增加了什么识别特征
5. 两个英雄分别增加了什么独有结构
6. 巫妖英雄如何体现巫妖，而不是死亡游侠
7. 新增了哪些 BodyRig 挂点
8. 新增了哪些 Mesh/材质/发光工具
9. 是否修改了 Unit、Common 或 Gfx 的公共 API
10. 是否影响碰撞、战斗、移动、弹道和性能
11. 在 Unity 中如何预览和验收
12. 已知限制和下一步改进
```

最终目标：让玩家在不依赖单位名称和 UI 标签的情况下，仅凭轮廓、材质、武器、动作和能量表现，就能快速理解“这是什么阵营、什么兵种、是否英雄、应该如何应对”。
